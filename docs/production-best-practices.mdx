## WebSocket connection reuse

**Open one WebSocket connection per call. Reuse it for every TTS request within that call. Close it when the call ends.**

Per-request socket opens dominate latency. Customers seeing 500 ms+ time-to-first-audio when they expect 100–300 ms are almost always opening a new socket per request.

```python
# Wrong: new connection per request
async def generate(text):
    async with client.async_connect() as conn:  # expensive!
        async for chunk in conn.async_tts(text=text, ...):
            ...

# Correct: reuse one connection for the call
async def handle_call():
    async with client.async_connect() as conn:
        for utterance in call_utterances:
            async for chunk in conn.async_tts(text=utterance, ...):
                ...
```

## Use streaming text input for lowest latency

Most LLM integrations wait for the full LLM response before sending to TTS. This adds unnecessary latency. See [Streaming Text Input](/streaming-text-input) for the pattern that achieves 100–300 ms time-to-first-audio.

## Use voicePromptId variants for speed and emotion

- For slower or faster delivery: use slow/normal/fast `voicePromptId` variants for the speaker instead of `tempo`.
- For questions: switch to the question `voicePromptId` for that sentence.
- For emotional shifts: switch `voicePromptId` between sentences — see [Core Concepts](/concepts).

## Concurrency sizing

Concurrency sizing and provisioning have their own page. See [Concurrency & Capacity](/concurrency) for the full explanation of how concurrency translates to in-flight requests and how to time pre-warming around model provisioning windows.

Quick reference: pre-warm **5–15 minutes before peaks**. Model provisioning is not instant.

## Always specify model explicitly

Never rely on SDK defaults. Always set `model="dd-etts-3.2"` explicitly so your integration is not affected by SDK version changes.

## Retry strategy

On `429 RateLimit` errors, retry with exponential backoff. Do not retry on `402 InsufficientCredits` — top up your balance first.

On `500` errors, retry once after a short delay. If failures persist, contact your Deepdub representative with the `generationId` from the response.

## Save the response for every request

Each TTS response includes a `generationId`. **Save it.** When you need to report a pronunciation issue, audio artifact, or any other quality problem, the `generationId` is what lets Deepdub trace exactly what was generated.

You can either include a `generationId` of your own on the request (any UUID) or let Deepdub assign one — either way, log the value returned in the response.
